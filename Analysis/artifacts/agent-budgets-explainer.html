Level 1 · Anyone can read this

A company card for an AI assistant

AI assistants can now do work on their own, and some of that work costs money: buying a report, paying for data, renting computer time. Today you have two bad choices. Hand the assistant your whole wallet and hope nothing goes wrong, or approve every purchase yourself, which defeats the point.

We give each assistant its own card with rules on it, the way a company gives an employee a card with a limit.

You setA budget and a list of shops it may use
It buysOn its own, with no clicks from you
It's stoppedWhen it tries to overspend or use an unknown shop
You cancelAny card in one click; the others keep working

The rules are enforced by Solana, a public payment network, not just by our app. So even if the assistant is tricked or hacked, it still cannot break them.

Level 2 · The pitch

Data by the question, not by the subscription

The mentor gave us three pieces of feedback. The tools for agent budgets already exist on Solana, so the infrastructure alone is not a product. We need one specific use case. And the value proposition has to be clean and unique, with the business idea in front.

The use case we chose: AI research assistants at consulting and VC firms. Analysts constantly buy data for different client projects. Today that means expensive yearly subscriptions and a month-end spreadsheet to work out which client to bill.

"Your AI pays for data by the question, in cents instead of €10,000 yearly licences, and every cent is billed to the right client automatically."

Not clean

"Capped, revocable spending delegation for AI agents using x402, enforced on-chain."

Clean

"Your AI assistant can buy things on its own, but it can never spend more than you allow."

Why this is unique, not just clean

  • Tiny payments. A card costs about €0.30 plus 2–3% per payment, so paying €0.002 for one API call is impossible. On Solana it costs a fraction of a cent.
  • No human in the loop. Cards need logins, 3-D Secure and SMS codes. An AI agent can't do that.
  • Proof per purchase. A card statement can't prove which agent bought what for which client. A Solana receipt can, and nobody can fake it.

Who pays us

  • Data sellers pay a small percentage per sale, because we bring them AI buyers they can't reach today.
  • Firms pay per seat for budgets, approvals and the client billing report.

The two-minute demo

  1. Ask the assistant: "Research Tesla's battery suppliers for Project X."
  2. It buys three data reports. Each payment links to the Solana explorer.
  3. It tries an unapproved data seller. Refused.
  4. It hits the project's budget. Refused.
  5. A partner approves one large purchase from a phone.
  6. The client billing report is ready to invoice.
Level 4 · Research

What already exists, and the gaps nobody has filled

Agents paying for things is a busy space. Most of the obvious ideas have been built, which is why the mentor pushed us to a specific use case. Payments between machines run on x402, a standard that lets a web server answer "payment required" with a price, and lets the caller pay and retry automatically.

Already built, so we don't rebuild it

IdeaWho did it
Capped, revocable agent budgets on SolanaA Solana "fixed delegation" program (devnet)
Pay actual usage up to a limit ("upto")Coinbase, announced live on Solana 17 Sep 2026
Bundling many tiny paymentsPayAI, public preview on Solana
Refunds through escrow and an arbiterx402r
Chargebacks for agents with AI judgesClawback, ETHGlobal New York 2026
Enforceable spending caps on HederaTally, Hedera x402 bounty winner, Aug 2026

Real problems with evidence

  • Services delivered before payment settles. A 2026 study found 31 vulnerabilities across 15 x402 payment services, including Coinbase, covering 99% of x402 transactions.
  • Usage billing trusts the seller. Under "upto" the seller picks the final amount up to the cap, and nothing checks it. Apify, a large API seller, says x402 billing "isn't good yet".
  • Agents tricked into spending. More than $150,000 was drained from an AI agent through prompt injection in 2026. Most protection still runs on a company server.
  • Small market so far. x402 volume is about $1M a month. This is a market that is forming, not a large one yet.

Where the old project came from

The code we are porting was written for ETHOnline 2026 (online, 4–16 Sep), on Hedera with ENS names. The folder name "ehl_switerland" made it look like a Swiss event; ETHGlobal has never run one in Switzerland. It moved real testnet money three times on 11 Sep and was submitted as Capability Descent, but it won no prize and was not a finalist. Cordon, a finalist, built almost the same mechanism.

Level 6 · Engineering

How the repository is organised

The repo is Mulaydm10/solana-hackathon (public). It is set up as a team project: work is split into lanes, each lane is one folder with a written contract, and every change goes through a pull request. Dhruv runs the design role and merges; Vedant's Claude Code session works as a worker.

Status: the planning is done and merged. The three code lanes are still empty. The code to port lives in the old Hedera repo, about 3,900 lines of TypeScript.

How a change gets in

  1. A task is an issue labelled with its lane, for example lane:core.
  2. A worker claims it by creating the ref claim/<issue>. Whoever creates it first owns the task.
  3. The worker codes inside that one folder only and runs the lane's check from docs/verify.txt.
  4. CI runs three jobs: lane (only allowed files changed), resolve, run (tests).
  5. Someone other than the author reviews; Dhruv merges. Nobody merges their own work.

The core rule, in code terms

check(agent, amount):
  if agent or any ancestor is revoked  → REVOKED / PARENT_REVOKED
  if amount > remaining(agent)          → OVER_LIMIT
  else                                  → ok, debit agent

grant(parent, child, cap):
  cap must be ≤ remaining(parent)        // a child never gets more than its parent
revoke(agent):
  cuts off agent and its whole subtree; siblings untouched
Why the refusal happens first

The server checks the rules before it quotes a price. If the answer is no, the payment service is never called, so no money can move by accident. On Solana the chain enforces the same limit a second time, so a bypassed server still can't overspend.
